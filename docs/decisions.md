# 决策记录与踩坑

> 记录「为什么这样做」，而不只是「做了什么」。便于将来质疑或推翻这些决定。

## 一、为什么用服务层包装而不是 DOM 选择器

**背景**：对话里的文件链接有两种 DOM 形状——Markdown 链接是
`<button class="…_fileLink_…">`，行内代码路径是 `<code><button title="…">`。

当时的替代方案有三个：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 给 `fileLink` 按钮加 `onClick` 包装 | 直接 | 依赖 CSS module 哈希类名，DSH 改样式就失效 | ✗ |
| 捕获阶段拦截 `[class*=fileLink]` 的点击 | 不用改源码 | 只管一种形状，且类名脆弱 | ✗ |
| **包装 `sidebarRight.openResource`** | 一处覆盖全部入口，不碰 DOM | 依赖方法名（非稳定契约） | **✓ 采用** |

**核心理由**：链接、行内代码路径、右侧文件树**全部经过 `openResource`**。
包一个方法覆盖三种来源，比维护三个选择器稳。

**代价**：依赖 DSH 内部方法名。已用启动自检（`selfCheck`）把「静默失效」变成「明确报错」。

**如果将来要推翻**：等 DSH 提供官方扩展点，或改成 patch 源码的方式（但那样升级即失效）。

## 二、为什么触发键是 ⌘ 而不是 ⌥

最初我建议 ⌥（Alt），理由是「⌘+点击在浏览器里是打开新标签页，可能冲突」。

**用户否决，理由更硬**：

1. DSH 里外部链接的点击处理本来就有 `metaKey/ctrlKey/shiftKey/altKey` 放行分支——
   按住 ⌘ 点 `http` 链接，代码主动 `return`，让浏览器原生开新标签。
   **「⌘ = 交给系统」在这个代码库里已是既成约定**，文件链接只是没跟上。
2. 浏览器/编辑器生态里 ⌘+点击普遍就是「交给系统/新窗口」，肌肉记忆一致。
3. 实测 ⌘+点击原本**毫无反应**，征用它不踩任何已有行为。

**结论**：⌘ 不是「用户主观偏好」，而是与既有约定一致。这个判断是对的，我当时的建议是错的。

## 三、为什么只认一个触发键，且按平台判定

**中间走过一次弯路**：最初写的是 `metaKey || ctrlKey`，本意是兼顾 Windows。
但在 macOS 上，Ctrl+点击被系统解释成**右键**，浏览器派发 `contextmenu` 而非 `click`。
这个分支在 mac 上基本是死代码，却扩大了触发面。

**改法**：用 `navigator.platform` 判断，mac 认 `metaKey`，其他认 `ctrlKey`，另一个键永不触发。

**原则**：除了这一个组合，**不接管任何点击**，全部原样交回 DSH 和浏览器。

## 四、为什么失败要回退预览

**初版行为**：宿主拒绝时只 `console.warn`，界面上什么都不发生。

**问题**：用户按住 ⌘ 点一下，看起来像「没反应」——正是当初 `dsh-file-opener` 让人困惑的
同一类体验。

**改法**：`openWithDefaultApp` 在宿主拒绝时 **throw**（把 `{ok:false}` 也当失败），
调用方 catch 后调 `original(address, options)` 回退预览。

预览自己会把「文件不存在」显示出来，用户至少知道发生了什么。

**教训**：静默失败比错误提示更糟。用户无法区分「功能没生效」和「操作没被识别」。

## 五、为什么 `consumeGesture` 改成「先判断、后消费」

**初版**：`openResource` 一进来就 `consumeGesture()`，然后再解析地址。

**问题**：按住 ⌘ 点了非文件资源（如 `dsh-resource://browser/…`）时，手势被白白消费掉。

**改法**：拆成 `isGestureHit()`（只判断）和 `clearGesture()`（消费），
**确认要接管之后才消费**。

影响很小（实际危害有限），但结构上更干净。

## 六、为什么最终用 npm 依赖而不是 `link:`

**过程**：
1. 最初用 `link:` 指向 `~/.dsh/local-plugins/`，好处是改代码即时生效
2. 用户随后从插件页装了 `dsh-file-opener`，**pnpm 重建 node_modules 时，符号链接被替换成实体副本**，
   版本退回旧的 0.1.0
3. 改成 `"^0.1.x"` npm 依赖，进锁文件，pnpm 正常管理

**教训**：`link:` 与 pnpm 的 `node_modules` 管理**天然冲突**。
如果你希望「改代码即时生效」，就必须接受「装别的插件时可能被覆盖」的代价。

**当前选择**：用 npm 依赖，接受「改代码 → 发布 → 升级 → 重启」的流程。
源码位置与运行位置**解耦**，源码放哪都不影响运行。

## 七、为什么迁移到 `~/own/20_tools/dsh-plugins/`

**原始理由**：`~/.dsh/local-plugins/` 是 DSH 的配置目录，不是个正经的代码仓库位置，
有被清理/重置的风险。

**我最初的建议更保守**（放 `20_tools/` 一级），但用户选择了建 `dsh-plugins/` 子目录。
理由是：将来第二个、第三个 DSH 插件有统一去处，且不污染 `20_tools` 的一级语义。

**顺带修正了 `~/own/README.md`** 里 `20_tools` 的描述，让规则能容下「独立发布的小工具」。

## 八、插件名的三次反复（教训）

| 版本 | title | 问题 |
|---|---|---|
| 初版 | `⌘ 点击用默认应用打开` | 把宣传语当名字，整句显示在插件列表里 |
| 0.1.2 | `Skip Preview` | 我自作主张改的英文名，没问用户 |
| 0.1.3 | `dsh-skip-preview` | 用户选定：与包名一致 |

**根因**：我没把「插件显示名」当成需要用户决策的产品外观，随手填了。

**教训**：
- `locale` 的 `meta.title` 是**卡片标题**，不是介绍
- 命名属于**产品决策**，不是技术细节，应该问
- 「我该直接做的」（修 bug、对齐版本）与「该问用户决定的」（命名、措辞、发布节奏）
  是两类事，不要混

## 九、npm 发布的踩坑记录

### staged publishing

npm 账号启用了 staged publishing，`npm publish` 会：

1. 首次发布时创建 `0.0.0-stage` 占位版本（**33 字节**，描述是
   "Temporary package placeholder for staged publishing"）
2. 真实内容进暂存区，**需要 2FA 批准才能上线**

我当时误判为「发布失败」，实际是「上传中」。**判断标准应该是 `dist-tags.latest`，
不是命令返回码。**

### 延迟

registry 更新有 **1–3 分钟延迟**。`npm publish` 返回成功后立刻查 `latest` 可能还是旧版。

### token 的矛盾建议（我的错误）

- 发布完建议用户「立即撤销 token」
- 下一轮要补发版本时又向用户要 token

**正确认知**：只要还会更新这个包，就需要持续可用的发布凭据。
按更新频率选择：长期 token / 每次临时建 / 自己手动发。

## 十、README 的两个坑

### 图片必须是绝对 URL

```markdown
![...](docs/demo.png)          ← GitHub 能显示，npm 显示破图
![...](https://raw.githubusercontent.com/<owner>/<repo>/main/docs/demo.png)   ← 两边都行
```

npm 不解析仓库相对路径。**只验证本地和 GitHub 会漏掉这个**。

### 英文版不能比中文版短一半

初版中文 138 行、英文 46 行，缺「实现要点」「已知限制」「源码安装」。
开源项目的主要读者是英文用户，信息不对等会直接劝退。

## 十一、验证方法论的教训

**问题**：我用「能不能装、语法对不对、bundle 有没有下发」验证，全是**机器视角**。
而破图是**读者视角**的问题——只有真的打开 npm 页面看才会发现。

同类漏检风险：
- GitHub 上 README 的表格、代码块渲染
- 社区帖子在手机上的显示
- npm 页面顶部 repository 链接是否可点

**改进**：发布后应该实际打开页面看一眼，而不只是跑脚本。

## 十二、Git 历史被污染

用 GitHub Contents API 上传文件（因为 `github.com:443` 当时不通）导致
**每个文件一次提交**，最终产生 9 条重复的 "v0.1.0" 提交。

**清理方法**：`git checkout --orphan` 重建单条提交，再 force push。

**如果重来**：优先解决网络/凭据问题用正常 `git push`，不要用 API 逐个传文件。

## 十三、会话/需求层面的教训

### 我误读了用户的核心动机

用户说「屏幕小，右侧预览窄，看不清」。我最初理解成「**想编辑**文件」，
据此反对「按文件类型分流」的方案（理由是编辑意图猜不准）。

**实际是**：「**想用整个屏幕读**」，与编辑无关。
这个误读导致我给出了一个基于错误前提的反对意见。

**教训**：用户描述现象（「窄」）时，要问清背后想做什么，不要自行填补动机。

### 反复发布 4 次（0.1.1 → 0.1.4）

原因依次是：文档后改没重发 → 名称写错 → 图片相对路径。
**每次都是可以一次做完的**。

**改进**：发布前把「代码 + 文档 + 元数据 + 展示效果」当成一个整体检查一遍。
